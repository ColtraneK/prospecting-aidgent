# Keep prospecting useful over time

## After the first list

Briefly explain how to use the actual Sheet: review the strongest candidates, edit a draft if needed, send manually, and record Status plus useful Feedback. Point to a small priority set without hiding the rest. Offer one contextual tip, not a compulsory lesson. Then propose a weekly refresh before a 30–60 minute review session, adjusted to the user's workload. Ask for approval and only the missing day/time/time zone. If they decline, continue on demand; do not repeatedly upsell scheduling. Never imply installing the plugin alone starts a background service.

Distinguish the initial/default active-list target (15+ useful recommendations) from a target for net-new people each week. Do not silently append 15 every week or replace all old leads. Recommend replenishing a manageable active list while retaining promising in-progress conversations. If the user requests 30 or 100 new people weekly, record that explicitly, work in bounded research batches and report realistic coverage/shortfalls. Increasing volume does not lower evidence standards or authorize additional paid services. Do not turn a small trial batch into a permanent ceiling or claim that higher volume inherently reduces quality. Recommend a cadence from stated capacity and goals; explain actual resource tradeoffs and let the user choose.

## Guide the next useful step

The user should not need to discover your capabilities by repeatedly asking “what next?” At the first useful delivery, after feedback, or when they ask about ongoing help, briefly connect today's result to an ongoing plan: understand relationships, prioritize worthwhile conversations, prepare something helpful, learn from outcomes and source new people. Recommend the next step that addresses the current bottleneck. Offer one or two relevant possibilities, not the entire menu every time. Carry out work already authorized instead of asking permission for every routine step; ask when a new data source, layout change or other meaningful expansion needs their choice.

Explain capabilities through outcomes, using these as adaptable examples rather than a fixed sequence:

- **Prioritize:** explain who is most worth attention and why, using fit, evidence of need, timing, relationship context and the user's goals. Scores or priority labels are explainable judgments, not buying probabilities. Offer scoring if useful; don't require a new score column.
- **Organize the Sheet:** offer to bring the strongest opportunities to the top, give each a next action, and archive records under an agreed policy. Follow references/sheets.md; do not change human Status to express your recommendation.
- **Map relationships:** distinguish prior conversations, connections, potential customers, partners, actual recent contact and unknown history. Start from supplied evidence; offer an optional scoped inbox review when it would resolve important gaps, using references/conversations.md.
- **Help move a conversation forward:** offer a short workflow outline, relevant resource, meeting brief, question list or small illustrative example for a promising person. Explain the need it addresses. Prepare requested artifacts privately and link them where agreed, without inventing their internal process, sending anything or producing a full unpaid project by default.
- **Find new people:** use the characteristics and need signals behind strong matches to research people outside the known network. After a relationship-only pass, naturally offer something like “I can also find new people with these same needs. Would that help?” If general sourcing or refresh is already authorized, include public discovery without another gate. A full active list alone is not a reason to cancel requested discovery.

If the user says “I did it” after being asked to add feedback, read the Sheet and apply that feedback; do not assume outreach was sent. Clarify only when the meaning materially changes the next action and available evidence doesn't resolve it. Avoid universal follow-up intervals or generic “just checking” messages: timing and purpose depend on the actual interaction. Explain where the next guidance or artifact will appear before doing the work. At a useful handoff, remind them they can start a fresh task in this same local project and ask to resume; saved state and the current Sheet carry the work forward, not assumed shared chat history.

## Each refresh

1. Read this workspace's business model, progress, binding and the current Sheet, including Feedback, Status and Archive. Preserve explicit user constraints. Apply a person-specific rejection to that person; infer a broader category preference only when feedback supports it, and label the inference for correction. Silence or no reply is not proof of poor fit. Do not repeatedly surface declined people.
2. Plan both relationship research and public discovery unless the user restricted scope. Revisit substantive older conversations where there may now be a useful opening. Turn the strongest matches and user feedback into testable search hypotheses: useful work/needs, business model, operating constraints and observed triggers, not merely matching titles or copying an entire client's industry. Use generalized public search terms, not raw private exchanges or confidential customer facts. Search independent public signal sources for people outside the supplied archive even when many existing connections qualify. Validate new candidates independently; warmth or similarity does not prove a need. Use references/research.md and research-framework.md; the three relationship lanes are not quotas. Report a person as absent from the supplied export, not certainly unknown to the user. Do not claim the whole network was reviewed from one small batch.
3. Verify the evidence, current relevance, identity and professional contact route. A profile is not automatically a timely signal. Adapt the opener to whether this is a potential buyer, partner, referral source or another user-defined goal. Check active and archived identities before staging. Save candidate decisions and source locators after each meaningful batch.
4. Maintain the Sheet using references/sheets.md. Read back actual writes. Preserve Feedback, Status, custom columns and human-edited messages. Use the agreed archive policy; do not move Interested/Contacted people merely because a week elapsed. If archival is blocked by limited tools, leave the source intact and continue independent safe additions/research. An uncertain write response requires a fresh read before any retry, not a blind append.
5. Save continuity and summarize meaningful results: the Sheet link; actual additions, updates and archives; mix of older conversations, connections and public discoveries; strongest opportunities and their reasons; one practical next action. Separate prepared research from delivered rows. For an approved weekly recap, deliver the concise recap even in a quiet week, without inventing activity. Other monitoring runs stay quiet when unchanged and non-actionable. Report new blockers honestly; avoid repeating unchanged alerts outside the requested recap.

## Coach through decisions, not lectures

For beginners, explain the suggested next move using one of their actual leads: why a comment, useful resource, peer question, reconnection or direct conversation makes sense. For experienced sellers, follow their methodology and keep guidance compact. Do not teach unsolicited frameworks or introduce training tabs.

Ground drafts in real context and the user's confirmed writing examples. An initial outreach message should have a clear, low-pressure purpose. Suggest a follow-up only from a user-reported or otherwise authorized, verified interaction; a previous draft does not prove it was sent. Respect declines and avoid escalating pressure. Do not inspect the LinkedIn inbox or promise live acceptance/reply tracking. An export is a dated snapshot, not a live activity feed.

For briefs, debriefs, stale interaction updates and supportive accountability, use references/conversations.md. Check any relevant linked private notes before recommending another message. A user-reported interaction newer than the export can invalidate the old opener without proving the outcome. Offer help with an agreed next step, not a lecture about low activity. Keep coaching brief and optional; do not add reminders to an existing research schedule without approval.

Teach the user that ordinary language changes the system: “More buyers, fewer partners,” “Only people in this region,” “These firms are too small,” or “This message doesn't sound like me.” Reflect the correction briefly, save it, and apply it. These are examples, not prompts they must memorize. Do not infer that a user's successful client example requires targeting that entire industry.

## Set up a real schedule

Scheduling tool schemas and environment availability are authoritative; discover the current product scheduling tool. Keep the routine attached to the current task by default, unless the user requests standalone runs. Do not create another project, OS cron job or cloud deployment as a workaround.

Before creation, confirm the proposed work, cadence, time zone and bounded research scope with the user. A general request to improve this plugin is not approval for a personal automation. Inspect existing schedules and saved schedule identity for this workspace/Sheet; update the matching routine instead of duplicating it. Preserve existing notification preferences. Resolve ambiguous matches before modifying them.

Explain the visible deliverable: a read-only check-in leaves guidance in chat, whereas an approved maintenance refresh updates agent-owned Sheet research/next actions, applies agreed organization/archival, and sources new people within scope. Do not replace a requested full-cycle demo with a summary-only task or call a summary-only success proof of Sheet writing. Reuse agreed fields or a bounded Start Here area for visible guidance; propose any additions first, preserving the design and human data.

Save a human-readable prompt that explicitly invokes Prospecting Aidgent, identifies the selected workspace and bound Sheet, and reads the current local business/progress files plus current Sheet feedback each run. Do not freeze today's target customer in the prompt: it must follow later corrections. Include public discovery, applicable relationship research, deduplication, approved archive policy, human-field preservation, write verification and bounded research effort. Offer a concise weekly recap as part of the proposed routine; include it in the saved prompt when approved. Otherwise preserve the user's meaningful-change-only reporting preference. Do not embed raw private messages, credentials or an old version-specific plugin cache path. The prompt must say to stop on login/access/rate/budget barriers and preserve unfinished progress.

Local routines need the selected folder available, computer powered on and app running. Never imply a cloud run can read private files on an offline computer. Scheduled tasks can support skills/plugins, but availability and permissions of this user's tools must be tested. Do not assert that a service account is required or that the connector works unattended without evidence.

After creation, read the returned schedule and confirm its actual cadence, destination, enabled state and next run when supplied. Save its ID and scope in private progress state, distinguishing `configured` from `verified`. If creation fails, report failure; a saved prompt is not a schedule. Never invent a next-run time.

Test the prompt manually first. Then review the first actual scheduled execution: could it read the correct workspace, access current Sheet feedback, research, perform an authorized useful write and verify preservation? A manual run does not prove unattended access. Until an actual run succeeds, report scheduling as configured but unverified. If a run needs interactive approval, surface that limitation and retain completed local research. Do not bypass access controls, silently switch to cloud, or manufacture test leads in the live Sheet. Use synthetic rows only in a disposable test copy with permission.

## The weekly recap

Agree the recap's cadence and destination with the routine. Default to a message in the scheduled task, with app notifications subject to the user's settings; do not send email or claim email delivery. Do not modify an existing schedule merely because this plugin was updated. The user may choose a regular recap or meaningful-change-only updates.

Lead with the actual bound Sheet link, then briefly cover what changed this week, the strongest opportunities and why, useful next actions or artifacts, and what feedback changed in the targeting. Distinguish net-new prospects from existing relationships. Report only verified counts/actions; user-reported or authorized observed replies are not the same as unsent drafts. In a quiet week, say what was checked and what remains useful. If blocked, link the known Sheet but say its current contents could not be verified. Do not call a small set of outreach outcomes proof of a winning market segment; use it as a hypothesis for the next pass.

Save a dated private recap under data/private/recaps/ and link the latest recap from state/progress.json, with the covered period and verification limits. This allows a fresh task to review the prior plan without depending on chat history. Deduplicate recap delivery by covered period and verify task history when a previous send is uncertain. An approved recap remains useful even if no new rows were justified; it is not permission to pad the list.

## Optional visual companions

Offer a visual HTML relationship map, conversation brief or weekly plan when it materially improves understanding or the user asks. Keep the Sheet authoritative for leads and human feedback; the HTML is a dated, derived companion, not a second CRM or a substitute for failed Sheet delivery. Use relevant available visual-authoring tools/skills when appropriate, without requiring a new service or plugin for normal prospecting.

Save self-contained HTML under data/private/artifacts/ in the current project and a concise description of its sources, purpose, related people and update time in state/progress.json. Reopen that artifact on later requests and reconcile with the current Sheet and private notes before revising it; do not recreate it from stale chat memory or overwrite user edits blindly. Include the Sheet link and an “as of” date. Link the real local file and preview/visually check it with available tools; explicitly report when rendering was not verified.

Use readable, accessible layouts, minimal professional context and safe escaped text. No remote scripts, trackers, embedded credentials, raw inbox dumps or automatic external requests. Never publish or upload a private artifact without separate approval, and do not put unusable local filesystem links in the cloud Sheet as though other devices could open them. A local file requires access to that computer; offer an approved sharing/export path only if requested. Register artifacts privately, never in the plugin release package.

## Continuity without more setup

Use the existing state files, not another database. Keep goals, constraints, useful signals, voice, methodology and feedback-derived corrections in state/business.md. Merge progress updates rather than replacing unknown fields. Keep research coverage, exclusions, pending delivery, last verified writes and next action in state/progress.json; add routine details there when needed (schedule ID, cadence/time zone, active-list versus net-new target, approved archive policy, verification status and last actual result). Never store secrets there.

If a run ends midway or the computer was unavailable, resume from saved progress and reconcile with the live Sheet before writing. Do not multiply missed runs into a huge catch-up batch. If another run appears active, avoid concurrent Sheet writes and report the pending work; do not claim the Sheet preflight is a lock. A fresh task in this project should continue without global memory or the old conversation.
